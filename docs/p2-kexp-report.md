# P2 事前検証: k 拡大と実リランカ実験レポート

## 1. 結論

AJIMEE 200 件で `k=5, 10, 20, 64` を比較した結果、候補幅を広げても実リランカの最終出力は 1 件も変わらなかった。4 条件すべてで mean CER は **0.29008046985634645**、Top-1 完全一致率は **14/200 = 7.0%** であり、k=5 を基準にした k=10/20/64 の改善幅は CER、完全一致率ともに **0** である。

平均処理時間として記録された `candidate_latency_ms` は k=5 の **61.78592772244891 ms** に対し、k=10 は **50.66158304186706 ms**、k=20 は **40.74597381000216 ms**、k=64 は **41.07583677114536 ms** だった。ただし k の増加に対して単調に増えておらず、今回の値だけから候補幅によるレイテンシ増加を確認することはできない。これは候補生成・リランカ処理の記録値であり、エンドツーエンド処理時間ではない。

**今回の結果だけを根拠に、現行構成のまま P2（文 K-best 合成再設計）へ投資する判断は見送る。** k 拡大と実リランカの組み合わせは、少なくともこの評価条件では品質改善を示さなかった。一方、文 K-best 合成を再設計すれば候補集合そのものを変えられる可能性はあるため、P2 を完全に不要と結論づけるのではなく、次の実装候補を「リランカの重み調整」ではなく「文候補生成・合成の検証」に限定するのが妥当である。再設計後は、候補集合が実際に変化したことを確認した上で、改めてリランカ効果を測定する必要がある。

なお、保存されている比較結果はすべて `hotchpotch/japanese-reranker-base-v2` を使用した条件である。リランカなしの独立した結果 JSON はこの実験成果物には含まれていないため、リランカ単体の寄与を数値として分離することはできない。本レポートで確定できるのは、**リランカを使用した条件において k を広げても出力が変わらなかった**という点である。

## 2. 指標サマリ

対象は AJIMEE 200 件。CER は全ケースの平均、完全一致率は正解と完全一致したケースの割合である。

| k | mean CER | Top-1 完全一致 | 平均処理時間 (`candidate_latency_ms`) | mean edit distance |
|---:|---:|---:|---:|---:|
| 5 | 0.29008046985634645 | 14/200 (7.0%) | 61.78592772244891 ms | 5.53 |
| 10 | 0.29008046985634645 | 14/200 (7.0%) | 50.66158304186706 ms | 5.53 |
| 20 | 0.29008046985634645 | 14/200 (7.0%) | 40.74597381000216 ms | 5.53 |
| 64 | 0.29008046985634645 | 14/200 (7.0%) | 41.07583677114536 ms | 5.53 |

指標の差分は次のとおりである。

- k=5 → 10: CER **±0**、完全一致 **±0 件**、mean edit distance **±0**。
- k=5 → 20: CER **±0**、完全一致 **±0 件**、mean edit distance **±0**。
- k=5 → 64: CER **±0**、完全一致 **±0 件**、mean edit distance **±0**。
- `candidate_latency_ms` は k=5 から k=10/20/64 でそれぞれ **-11.12434468151185 ms / -21.03995322244675 ms / -20.71009095130355 ms**。増加傾向ではないため、k に対する性能特性の結論には使わない。

## 2.1 本レポートにおける k の定義と、測定後に変わった前提

**この節は #6（Exact K-best・文全体ラティス化）のマージ後に追記した。保存済みの結果は #6 より前のコードで測ったものであり、以下の 2 点で現行コードの前提と一致しない。再測定なしに現行構成の評価として引用しないこと。**

### 測定時の k の意味

保存済みの結果は、当時 1 本のフラグ `--k N` で取得したものである。このフラグは 2 つの幅を同時に設定していた。

- **リランカ入力幅** — リランカに渡す候補数（`Converter.rerank_k`）。
- **出力幅・文合成ビーム幅** — `converter.convert(k=...)` のスパン内打ち切りと、`benchmark.convert_sentence` が直積結合後に候補を刈る `_deduplicate_candidates(combined, k)` の幅。

そのため本レポートの「k=N」は `--top-k N --rerank-k N` に相当する。この結合のため、**出力が 0/200 しか変わらなかった原因を、リランカ入力幅の寄与と文合成ビーム幅の寄与に分離できない**。

なお当時の `beam_width` の既定値は 64 であり、リランカ入力は元々この幅で頭打ちになる。従って **k=64 は `--rerank-k` 導入前の既定挙動にほぼ等しく、狭い条件は k=5 の側である**。

### #6 で変わったこと

#6 は `_input_spans` と `_deduplicate_candidates` を削除し、`convert_sentence` は文全体を 1 回の `convert()` で処理する。これにより 2 つの前提が変わった。

1. **`--top-k` の文合成ビーム幅としての役割が消滅した。** 現行の `--top-k` は出力幅とメトリクスカットオフのみを担い、`--rerank-k` はリランカ入力幅のみを担う。上で述べた「分離できない」問題は、構造的に解消している。
2. **スパン局所 Pruning がなくなった。** 5.3 で挙げた「文候補の合成・重複排除の段階で追加候補が最終リランカ入力に残っていない」という仮説は、その段階自体が存在しなくなったため、再測定で直接検証できる。

### 従って次にやること

現行 `main` で k=5 と k=64 を測り直してベースラインを取り直し、そのうえで `--top-k 5 --rerank-k 64`（狭く出力しつつ広くスコアリング）の非対称条件を測る。#6 によりリランカは文の断片ではなく文全体の候補を見るようになったため、リランカ効果そのものが以前と異なる可能性がある。

再測定時は、辞書のリビジョン（コミット SHA またはハッシュ）も結果 JSON に記録すること。保存済みの `results_kN.json` はどの辞書リビジョンで測ったかを記録しておらず、`24a422b`（IPADIC 取り込み）・`ba66606`（カタカナ表層抑制）との前後関係を後から確定できない。

## 3. span 数別分析

`analysis_kexp.json` の定義では、正規化入力中の連続するひらがな run が 1 本なら single-span、それ以外なら multi-span である。span 層別の件数は全条件で同じだった。

| 条件 | span 種別 | 件数 | 完全一致 | 完全一致率 | mean CER | mean edit distance |
|---:|---|---:|---:|---:|---:|---:|
| k=5/10/20/64 | single-span | 95 | 10 | 10.526315789473684% | 0.3407855276393473 | 3.705263157894737 |
| k=5/10/20/64 | multi-span | 105 | 4 | 3.80952380952381% | 0.24420446519553593 | 7.180952380952381 |

single-span は multi-span より完全一致率が高い一方、mean CER は高い。multi-span は平均 edit distance が大きく、文合成や複数スパンの誤りが残る構造が見える。しかし、どちらの層でも k=5 から k=64 まで指標はまったく変わらない。

従って、今回の実験では「single-span なら候補幅拡大とリランカだけで正解へ昇格できる」という仮説も確認できなかった。少なくとも実測上、single-span の 95 件でも新たな完全一致は発生していない。multi-span についても、文 K-best 合成の制約があるとして候補幅拡大の効果が隠れている可能性はあるが、今回の出力結果には現れていない。

## 4. 定性分析

### 4.1 正解に昇格したケース

リランカによって k=5 の出力から正解へ昇格したケースは **0 件** である。`changes_from_baseline` では k=10/20/64 の `promoted_to_exact_count` がすべて 0、ID リストも空である。

代表的な「昇格しなかった」例は次のとおりである。

- `ajimee-jwtd-v2-305`: 正解候補に「堅い殻を持つ卵を産むこと、高い代謝率」があるが、全 k で出力は `か大からを持つ卵を有無糊塗、高い大車律` のまま。CER は **0.6111111111111112**。
- `ajimee-jwtd-v2-965`: 正解は `外部の歌手の楽曲制作では` だが、全 k で `が慰ぶの歌手の楽曲政策では` のまま。CER は **0.4166666666666667**。

これらは候補幅を増やすだけでは、正解が最終的な 1-best に選ばれる状態にならない例である。候補が内部に存在していたとしても、リランカの再順位付けがその候補を 1 位へ動かすには至っていない。

### 4.2 悪化したケース

リランカによって k=5 の正解が失われたケース、または CER が悪化したケースも **0 件** である。`regressed_from_exact_count` と ID リストは k=10/20/64 のすべてで 0/空であり、`changed_hypothesis_count` もすべて 0 である。

したがって、今回の定性分析で「リランカが悪い候補を選んだ」といえるケースはない。悪化がないことは安全性の材料ではあるが、出力を一度も改善していないため、品質施策としての有効性を示すものでもない。

比較対象として、全条件で正解を維持したケースもある。

- `ajimee-jwtd-v2-412`: `バスが釧路駅から阿寒湖畔まで` を全 k で出力し、CER 0、完全一致。
- `ajimee-jwtd-v2-1154`: `これもまた全国で初めての` を全 k で出力し、CER 0、完全一致。

これらは k 拡大による変化が不要なケースであり、変更件数 0 という集計と整合する。

## 5. k を広げても出力が 0/200 しか変わらない理由

### 5.1 観測事実

`analysis_kexp.json` の baseline 比較は次の結果である。

| k | 出力が変わった件数 | 正解へ昇格 | 正解から退行 |
|---:|---:|---:|---:|
| 10 | 0/200 | 0 | 0 |
| 20 | 0/200 | 0 | 0 |
| 64 | 0/200 | 0 | 0 |

mean CER、完全一致率、span 層別集計もすべて同一である。従って「k を広げたが差が小さい」のではなく、今回の保存結果では **200 件のどの出力文字列も変わっていない**。

### 5.2 リランカスコアの結合重み

候補幅を広げても、最終順位はリランカスコアだけで決まらない。候補生成側のコストとリランカスコアを結合する際、リランカ側の差が既存コスト差を上回らなければ 1-best は変わらない。今回の結果では変更仮説が 0 件なので、次のいずれか、または複合が考えられる。

- k=10/20/64 で追加された候補が、現行 1-best を上回るほどのリランカスコアを得なかった。
- リランカスコアの重みが小さく、元の生成コストによる順位を逆転できなかった。
- 文候補の合成・重複排除の段階で、追加候補が最終リランカ入力に残っていない。

ここで重要なのは、今回の JSON から結合重みそのものを逆算できないことである。従って、特定の重み値が原因だと断定せず、次回は各候補の生成コスト、リランカスコア、結合後スコア、最終順位を per-case で記録する必要がある。

### 5.3 候補分布と文 K-best 合成

候補幅 k は、単一スパン内または中間候補の数を増やすだけでは、文全体の候補集合を増やすとは限らない。現在の文レベル合成で追加候補が切り捨てられる場合、k=64 を指定してもリランカへ届く文候補分布は k=5 と同じになる。

per-case の具体例では、`ajimee-jwtd-v2-305` と `ajimee-jwtd-v2-965` が k=5/10/20/64 の全条件で同じ hypothesis と CER を持つ。これは、k 拡大が最終文候補の順位に影響していないことの直接的な観測例である。逆に、候補分布が本当に変わったか、正解候補が何位に存在するかは、この JSON の `per_case` 出力だけでは判定できない。

### 5.4 判断に必要な追加計測

原因を切り分けるには、次の情報を k ごとに保存する必要がある。

- 文候補数と重複排除前後の候補数。
- 正解文字列が候補集合に含まれるか、その順位。
- 各候補の生成コスト、リランカスコア、結合後スコア。
- 1-best と 2 位候補のスコア差。
- single-span / multi-span ごとの候補数と正解候補の残存率。

これらを取らずにリランカの重みだけを調整しても、候補が存在しない問題と、存在するが順位が逆転しない問題を区別できない。

## 6. 最終判断

今回のゲート実験は、k 拡大と現行実リランカの組み合わせによる改善を **支持しなかった**。

- CER 改善: **0**。
- Top-1 完全一致の純増: **0 件**。
- 出力変更: **0/200 件**。
- 正解への昇格: **0 件**。
- 正解からの退行: **0 件**。

したがって、現行候補生成のままリランカへ追加投資することは見送る。P2 に進む場合も、目的はリランカの再調整ではなく、文レベル K-best 合成を再設計して「k を増やした候補が実際に最終候補集合へ届く」ことを検証することに限定する。再設計後に候補分布とスコア内訳を計測し、候補集合が変わった場合に限って、リランカの結合重みと品質改善を再評価する。

ただし 2.1 のとおり、この結論は #6 より前のコードで得たものである。#6 が文全体ラティス化によってスパン局所 Pruning を廃止したため、上記の「文レベル K-best 合成の再設計」は既に実施済みとみなせる。従って次の一手は新規の再設計ではなく、**現行 main での再測定**である。ベースラインを取り直したうえで `--top-k 5 --rerank-k 64` の非対称条件を測り、候補集合が実際に変わったか、リランカがそれを順位に反映できるかを確認する。
