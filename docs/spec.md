# BeME 仕様書（生きた要件書）

`2026-08-20` 初版。`2026-08-21` 第2フェーズの文脈対応モック実装に合わせて更新。

## 1. プロジェクト概要

LLM の要素と検索技術をフルに使った自作日本語 IME（かな漢字変換）。
転職活動のポートフォリオ（武器）として開発。

開発者: sarashin（検索エンジニア・マルチフェーズランキング/検索基盤が本職）

## 2. モチベーション

- 既存 IME の変換は「決定的に質が悪い」ことがある。文脈を読めない誤変換を毎回同じように再現し、苛立たせる。
- 既存 IME の文脈利用は局所的（N-gram・履歴学習のみ）。未確定文字列・段落トピック・後方の文脈をクエリにする機能はほぼ未実装。
- 検索業界で起きた進化（静的ランキング → 文脈込みの再ランキング）を IME に移植する。

## 3. 設計の三原則（壁打ち確定 2026-08-20）

1. **文脈を読む**: 現在の入力文字だけでなく、入力履歴（確定済み文）やカーソルより後ろの文字列もクエリにする。第2フェーズのモックで前文・後方文字列の入力経路を実装済み。
2. **ランキングで勝負する**: 変換候補の順位がすべて。検索のマルチフェーズランキング（retrieve → rerank）を変換に応用する。
3. **レイテンシが正義・ローカル動作**: 通信なし、限られた計算資源で動く前提。モデルサイズ・量子化・キャッシュ・段階的推論を設計に織り込む。

## 4. アーキテクチャ構想

変換を情報検索パイプラインとして再定義する。

| 検索 | BeME |
|---|---|
| インデックス構築 | 辞書（トライ/LOUDS 等） |
| retrieve（候補空間の構築） | 辞書引き + ラティス構築 |
| 一次ランキング（静的スコア） | ビタビ / K-best Viterbi（第1ランカー） |
| 再ランキング（文脈込み） | `Reranker`（キーワードモック実装済み・将来 LLM へ差し替え） |

- ビタビは「1本の最適経路」しか返さない → **K-best Viterbi（ビーム探索）**で複数候補（N-best）を生成する
- 第1候補と第2候補の**コスト差 = 確信度**。確信度が高い時は第1ランカーの答えを信じて LLM をスキップ（カスケード判定）
- 文節単位の候補表示には N-best パスの文節区切り一致フィルタ + 表記ユニーク化が必要（Mozc 方式・ビーム幅は文節表記の多様性基準で数十パス）

## 5. モック実装のスコープ（第1フェーズ）

- Python 製 CLI ツール（Python 3.11 以上、ランタイムは標準ライブラリのみ）
- チェックインする自作ミニ TSV 辞書（MeCab/IPADIC の取り込みは第1フェーズでは行わない）
- ひらがな（長音符 `ー` を許可）入力 → 辞書引き → ラティス構築 → ビーム幅付き K-best Viterbi → 複数変換候補
- 辞書にない位置には一文字未知語フォールバックを挿入し、妥当な入力のラティスを常に連結にする
- コストは語コストと POS 遷移コストの合計。候補表記は一意化し、コスト・表記の順で決定的に整列する
- 同音異義語を含む、8 件以上の手作り JSONL 評価ケース + **NDCG / MRR による精度計測**
- 第1候補と第2候補の**コスト差 = 確信度**を出力し、しきい値未満ならカスケード対象にする
- LLM リランクは第2フェーズ。第1フェーズは辞書ベースの候補生成と評価基盤に限定する

## 5.1 文脈対応（第2フェーズ・2026-08-21 モック実装）

壁打ちで「直接入力にない前後の文の文脈を見る」を優先着手と決定（τ 調整は後回しでよい）。

- CLI がコンテキストを受け取る: 前文（確定済み文・入力履歴）と後方文字列（カーソルより後ろ・構想）のオプションを追加
- Phase 2 リランカのインターフェースを定義する（LLM はまだ接続しない）
- モックリランカ: 文脈を考慮したスコアリングのシンプルな実装（具体方式は実装判断。文脈中の単語と候補表記の関連度等）
- 文脈付き評価ケースの追加: 「こうしょう」+ 文脈「歴史」→ 考証 が正解 / 「こうしょう」+ 文脈「商談」→ 交渉 が正解、のような文脈で正解が変わるケース
- 文脈付きケース込みで NDCG / MRR を計測できるようにする

### 第2フェーズのモック実装で決定した事項

- **文脈表現**: `ConversionContext(preceding, following)` を第2ランカーの入力とする。CLI 名は `--preceding-context` / `--following-context`。両方の既定値は空文字列。
- **リランカ契約**: `Reranker.rerank(candidates, context)` は第1ランカーの候補と文脈を受け取り、各候補を一度ずつ含む採点済みの決定的な順序を返す。スコアは小さいほど上位とする。
- **候補深度**: 文脈リランク時は `top_k` で切る前の表記ユニークな全候補を第2ランカーへ渡し、リランク後に `top_k` 件へ絞る。これにより `top_k=1` でも第1ランカーの2位以下を昇格できる。
- **モックスコア**: 候補表記ごとの手作り関連語辞書を使い、前文・後方文字列での関連語出現 1 回につき `1.0` を第1ランカーの経路コストから引く。`score = cost - 1.0 × 出現回数` とし、`(score, cost, surface)` で決定的に整列する。`cost` は第1ランカーの値を保持し、`score` を最終順位の値として別に出力する。
- **実行条件**: 前文または後方文字列が空でなければモックリランクを実行する。カスケードしきい値 τ は第1ランカーの確信度として引き続き出力するが、第2フェーズ開始時点では文脈リランクの実行可否に使わない。
- **評価形式**: JSONL の `preceding_context` / `following_context` は任意の文字列フィールドとし、省略時は空文字列とする。文脈付きケースも同じ NDCG / MRR 集計に含め、個別結果には使用文脈とリランク実行有無を記録する。
- **非対象**: LLM / Cross-Encoder 接続、学習済み関連度、τ の再調整は今回のモック実装に含めない。

## 6. 第1フェーズで決定した事項と今後の計画

第1フェーズでは、実装と評価を再現可能にするため次の値・方式を固定する。

- **辞書**: 自作ミニ TSV をリポジトリにチェックインする。語彙規模・網羅性は
  本番品質を目指さず、同音異義語と分割候補を検証できる最小構成とする。
- **K-best**: A* + k-shortest paths ではなく、決定的なビーム K-best
  Viterbi を採用する。`beam_width` は API/CLI から指定でき、既定値は 64。
- **カスケードしきい値 τ**: 初期値を `2.0` コスト単位とする。第2候補が
  ない場合は確信度を算出せず、カスケード判定もしない。将来、ホールドアウト
  データでマージンと誤りの関係およびリランク率曲線を測定してチューニングする。
- **評価セット**: 初期セットは 8 件以上の手作り同音異義語ケースとする。
  実運用で追加する場合は匿名化したオプトイン訂正のみを使う。評価結果は
  ケース・辞書・`k`・ビーム幅・しきい値とともに再現できる形で記録する。

第2フェーズで確定済み履歴と後方文字列を使う文脈リランクの契約とモックを追加した。
今後は大規模辞書、ローカル LLM / Cross-Encoder リランカ、未確定文字列のより詳細な表現を追加する。
